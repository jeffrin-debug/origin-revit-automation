## Small-sliver merge fix: studs, tracks, and drywall boards (2026-07-30)

- **Wall script:** (a) `corner_pullbacks()`'s existing degenerate-reset guard (`if run_hi-run_lo < ...: reset to full wall_length`) now triggers at `MIN_SAFE_SEGMENT_FT` instead of the bare `MIN_SEG_FT` - a short wall whose pulled-back run would land under 6in now uses its full un-pulled-back length instead, eliminating the sliver at the source. Merges a too-small rect into another rect in the same list that shares its full X-range (stacked in Y) or full Y-range (stacked in X) - covers exactly the observed DP-S001-021 case; does not attempt an arbitrary L-shaped merge.

## Cross-wall corner-notch gap fill (2026-07-30, wall script only)

**User-reported (screenshot, `ST-014-001` selected in the "ORIGIN Assembly" view):** a real, visible black gap between wall 014's drywall and the converging band walls (026/068/069) at a multi-wall junction - not a sliver, a genuine uncovered strip. Ground-truthed with `origin_bridge_measure_014_corner.py`: zero real boolean overlap anywhere at that junction (framing studs touch correctly), yet the two walls' independently-computed corner-butt logic (`DRYWALL_CORNER_WRAP_BY_FACE`) each only trims against its OWN detected corner, so neither wall's board covers the connecting notch left by the other wall's slightly offset modeled geometry. Confirmed model-wide via `origin_bridge_scan_all_corner_gaps.py`: this is a recurring pattern (real, nonzero, small XY gaps between DIFFERENT walls' boards at shared Z-bands), not a one-off. User confirmed a general, model-wide fix is wanted, and separately asked whether Revit's own "Join Geometry" tool could just merge two boards manually - answered no: it's a viewport-only seam cosmetic between two STILL-SEPARATE elements (same two ids/Marks after joining), not guaranteed to survive USD export as one mesh, and there is no native Revit command that merges two arbitrary elements into one.

**Fix: `close_small_cross_wall_gaps(warnings)`** (new function, wall script only, runs once after the whole per-wall loop, right before `ensure_export_view`). New constant `CROSS_WALL_GAP_FILL_MAX_FT = 0.5` (6in) bounds how big a gap it will ever close. For every pair of `DP-*` boards on DIFFERENT wall hosts that (a) share real Z-overlap, (b) have a small (≤6in) gap on exactly ONE axis while fully overlapping on the other (a diagonal/corner gap on both axes is left alone - not a face-to-face condition), and (c) are BOTH currently plain rectangular slabs (real solid volume ≈ bbox volume - never touches a board with an opening/partition cut, since rebuilding from a bbox would wrongly fill a real cut): grows the lexicographically-earlier-Mark board (deterministic, so a pair is never processed from both directions) to exactly close the gap, via a new `make_world_axis_box()` helper (picks whichever of X/Y is thinner as the panel's extrusion axis). Every extension is checked by REAL boolean intersection against every other nearby board before being committed; a candidate that would create a new overlap is skipped and logged, not forced through.

**Debugging journey (three distinct, real bugs found and fixed in sequence, each confirmed by live measurement, not assumed):**
1. **Mid-transaction `FilteredElementCollector` staleness** (same class already known from `collect_soffit_assembly_solids()`): the function's own board-collection scan couldn't see any of the 275 boards just created earlier in the SAME transaction (`small_gaps_closed: 0` on the first live test). Fixed with a `doc.Regenerate()` at the top of the function.
2. **10 real new DP-vs-DP overlaps, model-wide, once the pass was enabled** - found via `origin_bridge_full_overlap_sweep.py` (filters specifically for DP-vs-DP pairs, since this fix never touches `ST-*` marks). Confirmed via a controlled A/B disable test (`if GENERATE_DRYWALL and False:`) that the pass itself is the sole cause (0 overlaps off, 10 on, reproducibly). Root cause: a board can serve as "neighbor" (read-only reference) in one pairing and later become a "grower" itself in a separate pairing within the SAME pass - the per-pair safety check only ever compares ONE proposed extension against the model's state at that moment, so it cannot see a later, independent extension elsewhere in the same pass that ends up overlapping it once BOTH are actually applied. **Fix: an unconditional final audit-and-revert pass** - after all extensions in the main loop are done, every board that was extended this pass is re-verified by real boolean intersection against every other board's FINAL, fully-settled geometry; any that still overlap anything are reverted back to their pre-extension shape (rebuilt from a stashed `pre_bbox`, not re-derived) and the count decremented. This guarantees zero net-new overlap regardless of the exact ordering/interaction between independent extensions, rather than trying to make the per-pair check perfectly complete.
3. **The audit itself initially missed 1 of the 10** (`DP-031-003A`/`DP-060-002A`, the largest at 0.0347 cf - a real 2.5in mid-run overlap, not a tiny sliver). Root cause, confirmed via targeted debug logging: `grower["bbox"] = grower["ds"].get_BoundingBox(None)`, called immediately after `SetShape()` with NO intervening `doc.Regenerate()`, returned a STALE (smaller-than-actual) bbox - Revit's bounding-box query does not necessarily reflect a same-transaction shape change until the document regenerates. This stale bbox then fed the audit's broad-phase pre-filter, which wrongly excluded the true overlapping neighbor before the real boolean check ever ran (confirmed with exact numbers: the stale bbox's max X was 0.25ft short of the board's true new extent, which was exactly enough to make the broad-phase filter reject the one board it should have flagged). **Fix: stopped re-querying Revit for the bbox at all** - since the exact new extent is already known (it's precisely what `new_solid` was just built from), the bbox is now constructed directly from those same coordinates (`BoundingBoxXYZ` + `XYZ(nx0,ny0,...)`/`XYZ(nx1,ny1,...)`), which cannot be stale because it never asks Revit's cache. Same treatment applied to the revert path (reuses the stashed `pre_bbox` directly instead of re-querying after the revert's own `SetShape()`).
- **Verified live on `409 (1)` after all three fixes**: `small_gaps_closed: 69` (17 of the original 87 candidate extensions correctly self-reverted by the audit, including `DP-031-003A`), and `origin_bridge_full_overlap_sweep.py` confirms **`dp_vs_dp_overlap_count: 0`** model-wide. `full_verify.py`: same 4 pre-existing dormant-file failures as always (unrelated, unchanged).

## Wall-by-wall review methodology, and three real bugs from it (2026-07-31, wall script only)

**New review process** (user-directed): rather than running the whole building at once, walk the model one wall (or a small deliberate group) at a time via the bridge - select it in Revit, describe its real geometry/neighbors first (`origin_bridge_describe_wall.py`), place drywall scoped to ONLY that selection, inspect the result, note any new condition, then move on. Requires a selection-scoped run script since `origin_bridge_run_walls.py` force-selects every wall in the model before running (wrong for this workflow - it silently regenerated the whole 70-wall building when the user asked for one wall). **Fix:** new `origin_bridge_run_walls_selected.py` runs against whatever is currently selected in Revit, without expanding or clearing the selection - and `origin_bridge_run_walls_by_ids.py` (force-selects a hardcoded id list, for reproducing a specific multi-wall combination without manual Ctrl+select).

This process found a real, recurring pattern: **a doorway modeled as several separate short wall segments in a straight line** (a full-height wall + an elevated Z-restricted "header band" wall spanning the door width + a small full-height "jamb-stub" wall, rather than one wall with a hosted Door family and an opening cut) - not something the pipeline's opening-cut logic (`opening_rects`, header/sill/cripple framing) was ever exercised against, since it assumes openings are always a hosted family instance. Three real bugs surfaced, each confirmed live before fixing:

1. **A short wall's own corner adjustment can invert its drywall extent, dropping its coverage entirely.** `corner_face_extents()` computes each face's along-wall drywall range independently at each end; on a wall short enough (here `407836`, a 4.5in jamb-stub), the two ends' adjustments together produced `hi < lo` (an inverted range) - the resulting drywall cell had negative width and was silently skipped by the normal size check, leaving `ST-006-001/002` with studs but zero track and zero drywall (a real robot-navigation hazard: bare exposed framing). **Fix:** after computing both ends, clamp `hi - lo < MIN_SAFE_SEGMENT_FT` back to the wall's own full `[0, length]` - the same "never let a corner computation erase a real wall's coverage" principle already used for framing's `run_lo/run_hi` (`corner_pullbacks`' own degenerate-reset).
2. **That fallback then over-corrected**, letting a NEIGHBORING wall's own outside-corner wrap sail straight through it: `392686` (the header-band wall) wraps past its own physical end assuming open space beyond - true before `407836` had any coverage, false once it did. The candidate search deliberately skips collinear neighbors (they're not a corner to butt/wrap against), so nothing stopped the wrap from crossing a real wall sitting in its path - a genuine `DP-005-001A` vs `DP-006-002A/003A` overlap (0.016-0.03 cf x2). **Fix:** an explicit clamp - for every collinear neighbor found in the candidate list, never let a wrap extend past that neighbor's own physical span (checked on both the P0 and P1 side).

## Drywall intruding into a DIFFERENT wall's framing at a corner - fixed generally (2026-07-31)

**Confirmed as a systemic, recurring pattern, not a one-off** - found independently at TWO separate corners during the wall-by-wall review (`395748` into `ST-004-001`; `383365` into `ST-022-003`, plus a genuine `ST-022-003` vs `ST-023-001/002` stud-vs-stud overlap at the same corner). Root cause: two independent walls meeting at a corner with a small real gap between their MODELED endpoints (extremely common in this environment - 0.1-0.5ft offsets are the norm, not the exception, as documented throughout this whole review) each place their own studs/boards purely from their OWN geometry; neither wall's placement logic has any knowledge of the OTHER wall's exact stud position, so the two can physically clash right at the corner. Rather than chase down each corner's exact cause in `corner_face_extents()` (as attempted, inconclusively, for the `395748` case earlier), this is fixed with a general post-pass, matching the "verify with real geometry, fix conflicts found" pattern already proven for the cross-wall gap-fill.

**Fix: `trim_drywall_from_neighbor_studs(warnings)`** (new function, runs once after `close_small_cross_wall_gaps`, before `validate_wall_coverage`). For every `DP-*` board, finds any `ST-*` stud/track belonging to a DIFFERENT wall host that it really (boolean) intersects, and **subtracts** that stud's solid from the board - drywall always defers to framing it doesn't own. Never trims against the board's OWN wall's framing (that's normal, by-design proximity, not a defect). Only ever removes material (a boolean difference can't create a new overlap elsewhere); a board is left untouched (with a warning) if the subtraction would erase it entirely. New `OUT["boards_trimmed_from_neighbor_studs"]` count.
- **Verified live on `409 (2)`**: re-ran walls `383245`/`383365` - `boards_trimmed_from_neighbor_studs: 28` (scans the WHOLE current document, so it also caught and fixed corners among the other, previously-approved walls in the same pass). ## End-stud half-flange overhang left uncovered by drywall - fixed generally, revealed a second gap (2026-07-31)

**Confirmed as a real, universal, systemic pattern** - not isolated to `ST-023-001` (flagged earlier as a "broader design question, not yet decided"). User selected and named 5 separate exposed studs (`ST-016-001`, `ST-023-001`, `ST-057-002`, `ST-067-002`, `ST-070-002`); all 5 measured with the EXACT same numeric signature: the stud oversteps its host's own drywall board edge by precisely `FLANGE_FT/2` (≈0.0521ft, half the C-stud's 1.25in flange). Root cause: an end stud's CENTERLINE is placed exactly at the wall's own along-wall boundary whenever nothing wraps past it, so half its real width extends beyond that line by design - normal, correct framing practice - but the drywall board's edge lands flush at the SAME line with no allowance for the stud's own width, leaving that sliver of framing permanently exposed. Only visible on short walls in practice: on a normal-length wall a neighboring perpendicular wall's own corner-wrap board usually covers this same sliver as an incidental side effect; short jamb-stub-style walls often have nothing nearby to accidentally cover it.

**Fix:** in `corner_face_extents()`, as the LAST step (deliberately after the degenerate-reset, not before - see below), widen each end's face extent to reach at least `FLANGE_FT/2` past the wall's own raw boundary, but only ever WIDEN (take whichever of the current value or the widened value is more extreme) so a real wrap/butt that already reaches further is left untouched.
- **First attempt placed this step BEFORE the degenerate-reset and silently failed**: the widened range for a short wall (0.25-0.375ft) is still under `MIN_SAFE_SEGMENT_FT` (6in), so the degenerate-reset fired right after and threw the widening away every time, undetected until a targeted debug trace on `380595` showed `ext` still exactly `[0.0, length]` after the widen block had supposedly run. **Fixed by moving the widen step to run LAST**, after the degenerate-reset, so nothing downstream can undo it.
- **Second issue: widening every wall's board unconditionally introduced 30 new DP-vs-DP overlaps model-wide** - a widened board can just as easily reach into a NEIGHBORING wall's own drywall as into its framing, and `trim_drywall_from_neighbor_studs()` at the time only trimmed drywall against a neighbor's STUDS, not against a neighbor's own BOARDS. **Fixed by adding a Phase 2 to that same post-pass**: for every pair of `DP-*` boards from different hosts that really intersect, subtract the lexicographically-earlier mark's current solid from the later one's (arbitrary but deterministic tie-break; both boards are already independently valid, only the overlap sliver needs to go somewhere). Renamed/expanded docstring accordingly (function name unchanged).
- **Verified live on `409 (2)`**: all 5 named studs now have their FULL bbox range covered by their host's own boards (confirmed by direct comparison, not assumed) both before and after Phase 2's cleanup - Phase 2 only trimmed the EXCESS reach into neighboring walls, never touched the part legitimately covering each wall's own end stud. `origin_bridge_full_overlap_sweep.py`: `dp_vs_dp_overlap_count: 0` (was 30 mid-fix). `full_verify.py`: same 4 pre-existing dormant-file failures as always.
- New read-only diagnostic: `origin_bridge_check_exposed_studs.py`.

## Phase-2 neighbor-board trim: same-transaction staleness, third occurrence (2026-07-31)

**Confirmed live**: after regenerating a wall whose widened board now overlapped an already-existing neighbor board, the overlap sweep kept reporting the SAME pair unchanged even after Phase 2 (added earlier the same day) had, per its own debug trace, computed a CORRECT boolean difference (`diff.Volume` exactly matching `cut_vol_before - overlap`). Root cause, confirmed via targeted debug logging on the specific pair: `_solids_of()` re-fetching a board's geometry without an intervening `doc.Regenerate()` after that SAME board's own prior `SetShape()` call can return STALE (pre-trim) geometry - the exact bug class already documented twice this session (the wall gap-fill audit; the ceiling merge's bbox handling), now confirmed a third time in Phase 2 specifically. **Fix:** added `doc.Regenerate()` both as a boundary between Phase 1 and Phase 2, and after every individual successful Phase 2 trim (a board can be trimmed against more than one different-host neighbor within Phase 2's own double loop). **Verified live**: the specific persisting pair (`DP-017-002A`/`DP-033-001A`) resolved to `0.0` cf, `dp_vs_dp_overlap_count: 0` model-wide, and all previously-confirmed stud-coverage cases (`ST-016-001`, `ST-023-001`, `ST-057-002`, `ST-017-001`) remain fully covered after the fix.

**Lesson reinforced for any future post-pass that both reads AND writes DirectShape geometry in a loop**: `doc.Regenerate()` is required immediately after every `SetShape()` call whose result might be read back (via `_solids_of()`/`get_Geometry()`/`get_BoundingBox()`) later in the SAME pass - not just once at the very start of the function. This is now the third confirmed instance of this exact staleness class in this codebase; treat it as a standing rule for any new geometry-mutating post-pass, not something to rediscover each time.

## IMPORTANT: why the assembly can look "one-sided" in a normal view
The drywall now sits **flush INSIDE** the existing wall (assembly = wall thickness, centered), so its outer surface is coincident with the base wall's surface. Coincident surfaces z-fight → one face shows drywall, the other shows the base wall. This is NOT a placement bug and is independent of the Location Line (the script handles all `location_line_ref` values; changing a wall's Location Line to Centerline only shuffles the z-fight tie-break — not a real fix). The fix is the **"ORIGIN Assembly" isolation view** which hides the base wall. Verify there, not in the default 3D view.
